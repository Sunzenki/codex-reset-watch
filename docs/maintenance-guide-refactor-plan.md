## 1. 重构目标

将当前混合了现行规则、操作步骤、故障案例和逐日工作纪要的单一手册，整理为一份短小的入口手册和少量按任务读取的专题文档。

重构只改变文档组织方式，不改变产品范围、数据格式、安全边界、发布流程或用户授权要求。历史内容先迁移后精简，不直接丢弃仍有排障价值的信息。

目标结果：

- 主手册控制在约 300–450 行，能够一次完整读取。
- 主手册只保存当前有效规则、任务路由、标准流程和完成条件。
- 专题细节最多拆为三份常用操作文档，避免碎片化。
- 按日期记录的工作过程和旧提交信息进入历史档案，不再干扰日常维护。
- 会随时间变化的事实由代码、Git、Cloudflare 或线上页面核验，不在主手册中长期硬编码。

## 4. 不可删除或弱化的规则

以下内容在重构后必须仍能从主手册或其直接链接的专题文档中明确找到：

1. CRW 是非官方、人工整理的信息站，不自动抓取 X，不自动预测或修改公开数据。
2. 公开事实、单个或多个账号观察、编辑推断必须分层表达，不能把局部观察扩大为全量结论。
3. 倒计时归零不等于额度已经重置；确认帖时间也不等于后台精确执行时间。
4. PST/PDT、相对时间和模糊措辞必须保留歧义说明，不能伪造精度。
5. 内容更新必须同步检查数据、三语言文案、SEO 数据源、静态快照和受影响入口。
6. UI 修改后先本地生产预览并交由用户检查；用户明确同意后才能提交和推送。
7. `dist`、凭据、Cookie、Token、订阅 endpoint、`p256dh`、`auth` 和本地环境文件不得提交或记录。
8. 真实浏览器推送是外部消息发送，每一次都需要明确授权；部署不会自动授权发送。
9. 通知事件 ID 是幂等键；失败重试必须限定准确事件，不能无条件批量更新。
10. GitHub 推送成功不等于生产部署已经验证，通常还要核对 Cloudflare 部署 SHA 和线上权威信号。
11. 保留用户已有未提交修改，使用精确路径暂存，不使用 `git add .`。
12. 不恢复已否决的深色设计；继续保留键盘焦点、跳过链接和 reduced-motion 支持。

## 5. 应从现行规则中删除的内容

这里的“删除”仅指不再出现在现行操作规则中；有历史价值的原文会先放进历史档案。

- 具体某日的生产提交哈希和逐项工作过程。
- 当前事件仍是 2026-09-08 重置等已经可能过期的描述。
- Chrome、Firefox 曾经各成功收到多少条测试通知等一次性验收结果。
- 已修复故障的完整时间线和多轮尝试过程。
- 现有章节间逐字或近义重复的构建、SEO、通知和验收说明。
- 作为范例但不再承担规则说明作用的推广文案和标签列表。

不得删除已解决事故揭示出的当前约束，例如 Workers 必须使用 Web Crypto、推送服务返回 201/202 不代表用户必然看到通知、后台标签不是单语言发送开关等。这些结论应改写为简洁的现行规则。

## 7. 执行顺序

1. 先创建三个专题文档和一个历史档案，从原手册迁移内容，不删原手册。
2. 对专题文档内部去重，将历史案例改写为当前有效结论。
3. 重写主手册，使其成为任务路由和操作边界入口。
4. 逐条核对第 4 节的十二项不可丢失规则。
5. 使用标题、关键词和链接检查确认主手册与专题文档之间没有断链。
6. 检查 `git diff --check`，确认没有改动现有的 `README.md`、`experiments/` 或 `social/`。
7. 本次仅整理文档，不运行部署、不发送通知、不推送远端；是否提交由用户在审阅后决定。

## 8. 验收标准

- 主手册不超过约 450 行，且不含按日期排列的工作纪要。
- 新接手者仅阅读主手册即可知道项目边界、任务路由和完成标准。
- 执行内容、推送或部署任务时，只需额外读取对应的一份专题文档。
- 原 22 章中的安全规则、证据规则和授权要求均有明确去向。
- 所有相对链接有效，命令与实际 `package.json`、目录及代码保持一致。
- 没有把会变化的线上状态包装为永久事实。
- 历史档案明确标注“仅供背景参考，不作为当前操作指令”。
