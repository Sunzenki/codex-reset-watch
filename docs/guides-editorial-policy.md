# 资讯指南编辑与发布规则

> 生效日期：2026-10-21。适用于 CRW 资讯列表、独立文章及对应摘要、配图、元数据和译文。本文负责选题、采编、文风与发布质量；Markdown 字段和构建方式见 [资讯指南维护](guides.md)，发布事实见 [变更日志](../CHANGELOG.md)。

## 1. 栏目目标与授权

为 Codex、ChatGPT 和 OpenAI 用户提供能帮助理解变化、判断影响或解决问题的信息。优先回答：发生了什么、影响谁、现在是什么状态、用户能做什么。宁可少发，也不靠泛泛新闻、重复快讯或拼接材料填充列表。

用户已将本栏目文章的选题、搜集、核验、写作、编辑、置顶、精选、发布与更正交由 Codex 负责。符合本规则的常规文章无需逐篇重新确认；其必要的精确提交、推送、部署和线上核验属于文章发布流程。涉及已有无关修改时，先隔离本次文件，不能把它们一并发布。

本规则不代表已执行提交或部署，实际操作服从用户当前指令。旧示例已移除，当前源码有 23 个选题的三语正式稿（含 Day 18），本地预览已获用户确认；首次上线及后续更新仍须按第 9 节完成真实稿件、正式构建与线上核验，实际状态见变更日志。文章授权不扩展到发送真实浏览器通知、在 X 等平台发帖、付费订阅或站点基础设施变更。这些操作遵循各自授权。

每次开展采编时主动检查第 3 节来源。当前未设置定时任务，不承诺会话之外持续监控；如后续安排定时采集，仍须经过事实核验和本文发布流程，不能把来源 feed 直接转成文章。

## 2. 选题与发表门槛

| 优先级 | 题材 | 应带给读者的信息 |
| --- | --- | --- |
| 优先处理 | Codex 等相关服务故障、登录或任务异常、重要回归 | 受影响组件、症状、官方进展、可用的应对办法与恢复依据 |
| 重点跟进 | 额度、重置、计费或套餐策略变化 | 变化前后、适用套餐/客户端、起效或分批范围、用户如何确认自身情况 |
| 重点跟进 | Codex CLI、IDE、桌面端、Web 的实质更新 | 哪项任务受益、入口或版本、使用条件、兼容性及必要迁移 |
| 按需撰写 | 实用教程、排错和机制解释 | 真实问题、准确路径、判断方法；有帮助的理解也算收获，不强加操作步骤 |
| 有明确影响再写 | OpenAI/ChatGPT 其他产品变化 | 与本栏目读者实际使用的关系，避免泛化为所有 AI 行业新闻 |

立项前在任务记录中写清目标读者、具体问题、已有站内文章、关键来源，以及相对原文增加的价值。信息增量可以是适用范围梳理、前后对照、时间换算、步骤验证、错误识别或对用户工作的影响，不要求凑固定条数。

不把媒体通稿、融资估值、泛行业评论、没有可核查依据的传闻、情绪热帖、重复产品宣传作为发稿主体。媒体或社区可以帮助发现问题，但关键事实应回到一手来源。没有独立增量时，更新已有文章、补入相关说明，或不发。

同一故障用同一个事件页维护进展；同一策略的修正更新原文。新的独立故障、实质规则变化或确有独立任务的教程才另建文章，不把每次状态变化拆成薄快讯。没有日更数量、最低字数、固定 H2 数量或每篇 FAQ 的要求。

## 3. 来源渠道与核验

### 3.1 每次采编检查的来源

| 渠道 | 用途 | 核验重点 |
| --- | --- | --- |
| [OpenAI Status](https://status.openai.com/) 及具体 incident、历史记录 | 故障及恢复进展 | 打开事件详情，记录组件、各次更新和准确时间；首页总状态不能替代具体事件 |
| [OpenAI 帮助中心](https://help.openai.com/)、[Codex 套餐说明](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan)、[官方产品文档与更新日志](https://developers.openai.com/codex/changelog/) | 功能、额度、套餐、迁移与使用限制 | 实际读取当前条目、日期与适用条件；旧地址重定向后核对官方目标 |
| [OpenAI Codex 官方仓库及 Releases](https://github.com/openai/codex/releases) | CLI 版本、修复与已知问题 | 稳定版/预发布版、平台、实际发布版本；Issue 报告与已确认修复分开 |
| [Tibo @thsottiaux](https://x.com/thsottiaux)、[OpenAI @OpenAI](https://x.com/OpenAI)、[OpenAI Developers @OpenAIDevs](https://x.com/OpenAIDevs)、[ChatGPT @ChatGPT](https://x.com/ChatGPT) | 及时发现预告、Codex/API 开发更新、产品范围和后续纠正 | 打开原帖、完整线程与作者回复；发布时确认账号身份和语境，不以昵称、认证标记或转帖单独认定身份 |
| 常规联网搜索、官方公告及有关产品团队公开说明 | 查漏、寻找原始入口与交叉核验 | 检索结果只作线索，实际打开原文；社区体验保留其账号、版本与条件范围 |

这些入口是采编清单，不是全部内容都值得转发。来源地址和产品名可能变化，使用时重新核对；本文不固化具体套餐额度或当前故障状态。

### 3.2 证据如何使用

- 官方文档、明确公告、状态事件和已发布版本证明其实际表述的事项；员工原帖按作者说法归因，不自动等同于覆盖全体用户的产品承诺。
- X 可以作为明确预告的直接来源。若只有原帖、没有执行确认，就报道“预告”及其范围；不能为了赶稿补写已经生效。短帖内容足够明确时不强凑第二来源，多家转载同一帖也不算独立佐证。
- 官方实测、编辑实际验证、用户账号观察、编辑分析分别表述。单个账号看到额度变化不能推导全体到账；Issue 或投诉不能单独证明全站故障。
- 来源有冲突时核对时间、版本、对象和后续修订；关键冲突仍未解决就缩小结论或保留草稿。不能访问的原帖不能标成“已核验”，截图和搜索摘要不能代替必要的原文核验。
- 发布前重新打开易变的关键来源，记录本轮核对时间。较旧资料可以支持稳定机制或教程，但要核对它是否仍适用；“最新”必须有实际检索和日期依据。

关键事实的任务记录至少包含：原始 URL、作者/机构、实际读取时间、来源发布时间或版本、支持的结论、适用范围及尚未解决的缺口。不要把整篇来源、凭据或私人账号信息复制进仓库。

X 原站被抓取工具限制时，可使用用户授权的 Chrome 读取公开原帖。镜像、聚合页、截图用于寻找入口；核验记录应注明实际读取方式，不能把镜像可访问写成原站已读。新增员工或团队账号时，先核对与产品的关系，再按具体职责使用其说明；不把员工个人回复一律当作正式政策。

正文在相应结论附近放必要的来源链接，末尾 `sources` 汇总主要出处；正式文章的核心外部事实应有外部一手来源，不能只用本站旧文自证。Markdown 的 `sources` 现有字段仅为 label/url，核对时间、版本与证据说明放正文或任务记录，不虚构未被编译器支持的字段。

### 3.3 原帖评论与系列目录

- 查看对应原帖下点赞较高且与使用问题直接相关的回复，优先读作者/团队补充、适用范围、具体入口、异常条件与有依据的质疑。点赞只辅助筛选；不使用固定点赞门槛，也不把默认排序或评论样本当作民意统计。
- 引用评论时保留链接、作者和本轮读取时间；只有需要说明热度时才写当时点赞数。读完“显示更多”或进入完整回复后才能概括被截断部分。图片、玩梗、推广和无依据传闻不为丰富版面硬塞进文章。
- 产品团队回复支持其明确表述的范围；用户反馈按账号观察或观点表述。评论可以提出需要核对的问题，不能单独证明全站故障、长期额度策略、价格或所有用户的体验。
- 连载目录按实际起点、天数、时区归档，区分预告、完成确认和未知状态。目录、标签和统计来自同一批日文章字段；同一天多种内容可重叠，普通重置与储备预告分开。直播未核实具体交付时不计为新功能。
- 未到日期或尚未核实的日期只保留无链接空位。按天建独立页是本系列明确的阅读需求，正文仍须提供各日范围、证据与有用解释；不批量换标题造重复薄页。来源编辑时间、事件时间和本站首次公开日期分别记录。

首轮系列与评论的事实底稿见 [Tibo 28 天计划采编记录](tibo-28-days-source-review.md)。

## 4. E-E-A-T 的具体执行

Google 建议以人为本、提供原创价值并建立信任；E-E-A-T 本身不是一个具体排名因子，也没有“通过 E-E-A-T 认证”的发布证书。以下是本栏目的编辑执行要求，不是 Google 给出的打分表。[官方说明](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

| 要求 | 本栏目怎样落实 |
| --- | --- |
| 经验 | 声称“实测”时说明实际环境、步骤、时间及观察结果；只读文档就按文档分析写，不虚构账号经历、截图或效果 |
| 专业性 | 讲清额度窗口、客户端、套餐、版本、模型和状态术语的区别；教程兑现关键输入、入口、操作和结果判断 |
| 权威性 | 关键结论链接相关一手出处；身份、范围和时间可追溯；不捏造专家资历、业内共识或 OpenAI 官方关系 |
| 可信度 | 明确 CRW/WarpNav 为非官方维护方；署名、采编方式、来源、更正和日期真实，内容承诺与证据相符 |

Codex 负责检索、整理与写作时，公开编辑说明或文章正文应如实说明其参与方式；署名使用真实维护组织，不虚构一个人工记者。没有站长逐篇审阅就不能写“已经人工审核”；生成内容也不能包装成第一手体验。

禁止批量改写来源、低价值翻译拼接、堆关键词或为了“新鲜”改日期。AI 可以辅助采编，但不替代核验和有用的信息增量。[Google 垃圾内容政策](https://developers.google.com/search/docs/essentials/spam-policies)

## 5. 写作与文风

本节参考主站 `codex-workspace/rules/warpnav-publishing-rules-post.md` v5.33（2026-10-19）的 §1.3–1.9、§2.5，以及同目录 `warpnav-dynamic-content-architecture-rules.md` 的 §1.2、§2.3 和模块选择原则。保留其读者价值、自然表达和证据要求；CRW 的格式、字段及发布流程仍按本仓库执行。

- 开篇尽早说清本篇的关键变化、问题或判断，不用“随着 AI 快速发展”“引发广泛关注”等通用背景铺垫。故障稿先交代当前状态；教程先交代要解决的问题与必要起点。
- 用熟悉产品的人把事情讲清楚的语气。常用词、具体场景和连贯解释优先；术语、命令、错误码和必要条件保持准确，不为了口语化损失精度。
- 已核实事实直接写。争议、预测、厂商效果宣称、作者观点和账号观察保留必要归因，不把每句都写成“根据官网”“笔者查阅后发现”。
- 编辑判断要有理由。可以说明一项变化为何有用、哪里仍不清楚；纯事实更新无需强行制造推荐结论，不替产品写营销评价。
- 结构按本篇任务选择。故障按症状与进展组织，更新解释变化与影响，教程展开关键路径；不统一套“概览—功能—优缺点—FAQ—总结”。下节给出的是应回答的信息，不是必填标题模板。
- H2/H3 方便目录定位，尽量简短但保留完整语义；长解释放正文。段落讲因果，列表放并列项，有顺序的操作用步骤，共同维度的比较用表格，不为版式变化硬加模块。
- 重点讲容易卡住的地方。实际入口、条件、输入、输出和验证方法按承诺展开；不把“按需设置”“查看官网”“自行尝试”当作完整教程。
- 不用“重磅”“炸裂”“史诗级”“彻底颠覆”“全网最全”等无证据措辞，不把每段写成“值得注意的是—建议—总结”。已经解释清楚就结束，不强求每章总结或文末升华。
- 保留自然短句、口语、恰当比喻和有依据的偏好；故障、额度、收费和安全信息保持清楚。幽默按题材使用，不强加网络梗，也不拿用户损失作调侃。
- 标题、列表简介、首段、正文、SEO 描述和图注表达一致；摘要独立概括核心信息及阅读价值，不复制第一段或堆关键词。FAQ 只回答正文尚未解决、确有依据的问题。
- 修订旧文优先保留准确有效的解释、例子和步骤。删减要有错误、过时、重复或无关等理由，不为缩短篇幅或统一目录丢失内容。

表达示例仅说明文风，不代表当前事实：

| 避免 | 采用 |
| --- | --- |
| OpenAI 重磅升级，Codex 用户迎来史诗级利好！ | 标题直接写清 Codex 改了什么，以及影响哪个套餐或客户端 |
| 根据官网信息我们发现，这一变化值得用户持续关注。 | 直接解释该变化怎样影响任务；若范围尚未公布，就在相关句旁说明 |
| 官方已经修好了，大家都能正常使用。 | 区分“官方事件已标记恢复”和“本站某个环境验证通过”，按实际证据写 |

不移植主站的 WordPress HTML、`[toc]`、分类 ID、SEO 自定义字段、链接纯文本惯例或固定封面参数。CRW 使用 Markdown、自动目录、可点击的来源链接和现有森林手账视觉；不因参考文风而修改主站内容。

## 6. 不同题材必须讲清的信息

### 故障与恢复

1. 具体症状、产品和受影响组件；区分 Codex、ChatGPT、API 以及不同客户端。
2. 事件原始链接、当前官方状态、最新核对时间，以及主要进展时间线。保留 investigating / identified / monitoring / resolved 等原意；不要把“监控恢复”提前写成“完全解决”。
3. 已确认的影响范围、开始/恢复时间；未给出的原因、人数、套餐或恢复 ETA 不自行推算。
4. 有依据的临时办法、适用条件和验证方式。服务端故障不能随意建议清缓存、重装、删配置或反复重试；有费用或任务丢失影响的操作须说明条件。
5. 恢复后更新标题中已失效的进行时措辞、首段、时间线、摘要与置顶状态，保留原始发布日期和事件档案。

状态页披露的是聚合服务情况，不能证明某个账号一定正常或异常；官方首页正常也不足以否定用户问题。[状态页说明](https://status.openai.com/)

### 额度、套餐与重置策略

区分套餐额度、模型限制、滚动窗口、额外购买、临时加量和储备重置；不能用“一律翻倍”等说法抹去条件。列清变化前后、官方给出的适用对象、持续时间、推出方式和账号确认入口。只有文档说明或实际观察到的值才能写具体数字；单次重置不等于永久额度政策变化。

原帖发布时间、事件预计时间、公开确认时间、本站发布时间和实际观察时间分别记录。倒计时归零不证明执行完成。涉及首页与历史事实时，按 [内容与数据规则](content-and-data.md) 同步权威 JSON，不能只改文章。

### 产品更新与教程

产品更新说明实际改变的能力、客户端/版本、可用入口、限制及对原有工作流的影响；预发布不能写成稳定版全量可用。教程写清起点、关键操作、可观察结果和下一步判断，标明官方示例与实际验证的区别。只涉及机制解释的文章可以用准确例子讲清差异，无需硬加安装命令。

## 7. 列表和文章的 SEO 发布要求

### 7.1 资讯列表

- 栏目标题与简介清楚说明范围；每条文章显示真实标题、摘要、分类和发布日期，通过正常 `<a href>` 到达独立文章。置顶/精选体现重要性，不把旧文改成新发布日期。
- 列表用 CollectionPage / ItemList 等合适的结构化数据，不能把整个聚合页标成一篇 NewsArticle；数据与该 URL 的实际内容一致。
- 分页有独立可访问 URL 和可抓取的前后页链接，不能只靠点击按钮或 `#` 切换。若使用分页模型，每页 self-canonical，不能将第二页一律 canonical 到第一页。[Google 分页说明](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)
- 四个固定分类是独立主题归档：为实际内容设置专属标题、描述、H1、简介与主题词；有正式文章时 index,follow、self-canonical，并进入 sitemap，真实对应语言的第一页建立 hreflang。排序、返回状态和临时参数不形成新的搜索落地页，文章返回状态参数指向干净 canonical。[重复 URL 规范](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)
- 空栏目、示例、预览不提交索引；不为关键词排列、同义分类或 URL 参数批量生成重复页面。主题词应自然出现在标题、描述和真实内容中；meta keywords 按需保存，但不作为 Google 排名依据。

### 7.2 独立文章

- 一篇解决一个明确问题，有唯一稳定 URL 和清楚的 H1；`title` 与正文同语言、准确描述主题，不堆关键词。[标题指南](https://developers.google.com/search/docs/appearance/title-link)
- `summary` 对应实际内容，作为列表简介和描述的当前统一数据源。描述没有 Google 规定的固定字数门槛；按含义和展示效果写，不把原六页的 150–160 字符校验移植成文章质量标准。[摘要指南](https://developers.google.com/search/docs/appearance/snippet)
- 发布日期是本站文章首次公开日期，更新时间对应实质修订；事件日期放在正文中标清。不能倒填成来源发帖日、使用未来日期，或只改时间骗取新鲜度。可见日期、结构化数据与 sitemap 的相关日期相符。[日期指南](https://developers.google.com/search/docs/appearance/publication-dates)
- 连载回顾在文章头部和总目录日历使用明确标注的“系列日期”，描述事件归档；资讯列表统一显示真实 `publishedAt`，按英文 UTC、简中及繁中 UTC+8 换算。真实发布日期也在正式文章来源区域可见，并与 Article / sitemap 一致。未发布预览稿不填写 Article 的 datePublished/dateModified，避免把本地创建时间伪装成已公开日期。
- 文章使用 Article 或适用子类型，headline、datePublished、dateModified、author、publisher 与实际页面一致。作者身份可核查，不捏造履历或审核；结构化数据只能描述页面真实内容。[Article 指南](https://developers.google.com/search/docs/appearance/structured-data/article)、[结构化数据通则](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)
- 有正文、主要标题、来源和相关日期的静态 HTML；JavaScript 加载前后语义一致。正式页面的 canonical 指向自身干净地址，文章返回列表用的 query 不形成重复文章索引。
- 有真实译文才建立相互对应的 hreflang，每种语言各自 canonical；不让未翻译正文冒充对应语言，也不以跨语言 canonical 合并真正译文。[多语言指南](https://developers.google.com/search/docs/specialty/international/localized-versions)
- 图片服务理解：步骤优先真实界面或可验证示意，装饰图不冒充实测。信息图片有准确 ALT，装饰图可空 ALT；Article 的 image 应代表这篇内容，不能把通用品牌 OG 图默认当文章内容图片。无合适图片可以先不填可选 image，不为填字段制造图片事实。
- 主要内容可在手机阅读、链接和目录可用、图片有尺寸且不过度拖慢页面；广告不能遮挡正文或伪装成操作入口。实验室性能结果和真实用户 Core Web Vitals 分开记录。[页面体验指南](https://developers.google.com/search/docs/appearance/page-experience)

正式 sitemap 只收录可索引的 canonical 列表与文章，lastmod 反映真实内容变更；缺失页面返回真正 404/410，有对应替代内容才做准确重定向。生成 llms.txt、通过构建或写入 JSON-LD 都不代表 Google 已抓取、收录或保证富结果；相关结果以实际工具或线上证据记录。

## 8. 采编、发布与更正流程

1. 查阅本规则、栏目维护和工作区未发布改动；检索一手渠道并核对同题旧文，决定更新旧文、新建或不发。
2. 完成事实底稿和读者收获判断。新建/实质改写按本篇任务拟大纲，先用 `draft` 保存；不把样例直接改状态当成正式新闻。
3. 写作并审读全文、摘要及标题，检查证据、范围、时间、自然表达和主要承诺。需要插图时先完成正文，选用有依据的资料或示意；封面不作每篇必配项。
4. 发布前重查易变来源；确定本站实际首次发布时间，系列日期单独记录，后续文章持续执行[日期显示规则](guides.md#日期显示规则)，按真实译文发布。检查置顶/精选是否仍有价值。故障、额度与操作建议的关键缺口未解决时保留草稿。
5. 将核验完成的文章设为 `published`，执行 `pnpm build` 并检查受影响 HTML、链接、元数据、robots、canonical、hreflang、JSON-LD 和 sitemap；内容变更同步必要文档与 CHANGELOG，运行 `pnpm docs:check` 和 `git diff --check`。修改编译器或状态规则时增加 `pnpm test:guides`；纯规则文档不重复应用构建。
6. 检查正式构建的本地生产预览，确认真实内容、桌面/手机和受影响译文；核对列表月份、日期栏及行内日期均为对应语言时区的实际发布日期，系列日期仅在详情和日历中显示。普通文章无需另等逐篇批准；UI 结构修改仍按站点预览流程执行。绝不部署 `build:preview` 产物。
7. 精确暂存本次内容及必要代码/说明，提交推送后按 [部署手册](deployment-troubleshooting.md) 核对提交 SHA、Cloudflare 生产部署和实际 URL/静态输出。仅在完成对应阶段后记录“已部署”或“线上已验证”。
8. 后续采编或安排的检查发现实质变化时更新原文。涉及错误结论、范围或操作建议时填写 `corrections`，同步受影响摘要、标题、译文和数据；小标点修正不刷新日期。同一事件闭环后取消过时置顶，保留有价值的历史说明。

失效教程在正文开头标出过时条件，并尽量更新；合并重复稿保留准确替代 URL 和重定向，不静默删掉用户仍在使用的入口。更正和撤回记录说明原因，不用新稿掩盖旧错误。发现问题后在当前授权采编中处理，不声称存在未配置的后台值守。
